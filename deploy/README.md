## OCR-Worker (WP-O2)

Der Worker (`App worker --kinds dms.ocr`) ist ein eigener Dienst mit eigenem Image: `Dockerfile.worker` (Ubuntu 24.04, ocrmypdf, Tesseract `deu`+`eng`, Ghostscript, poppler; Lizenzen `docs/LIZENZEN.md`). Das Backend-Image bleibt ohne OCR-Werkzeuge. Der Worker hat keinen Port, liest Aufträge per Lease aus der Datenbank und darf nur nach `/tmp` (tmpfs) schreiben (read-only Root); mehrere Worker sind sicher (jeder Auftrag wird genau einmal wirksam).

```
docker build -f Dockerfile -t ghcr.io/ORG/lab-hub:1.2.0 .          # Backend (wie bisher)
docker build -f Dockerfile.worker -t ghcr.io/ORG/lab-hub:1.2.0-worker .        # Worker; Standardname = <LABHUB_IMAGE>-worker, überschreibbar mit LABHUB_WORKER_IMAGE
```

Einstellungen (alle optional, als Umgebung des Dienstes): `OCR_TIMEOUT_SECONDS` (Gesamtzeit je Dokument, 600), `OCR_MEMORY_MB` (Adressraumlimit je Werkzeugprozess, 4096; Container-Limit zusätzlich `OCR_WORKER_MEMORY`, 6g), `OCR_MAX_PAGES` (300), `OCR_LANGUAGES` (`deu+eng`), `OCR_JOBS` (2), `OCR_DEHYPHENATE` (`false` schaltet die Silbentrennungs-Bereinigung ab), `DMS_OCR_ENABLED=false` am Backend (Uploads reihen dann keinen OCR-Job ein). Der Worker prüft beim Start Werkzeuge und Sprachpakete und beendet sich mit Fehlermeldung, wenn etwas fehlt. Objektspeicher: wie das Backend (`OBJECT_STORE*`); bei `OBJECT_STORE=fs` muss das Volume auch am Worker hängen (Compose-Datei nicht vorbereitet), sonst `db` oder später S3.

Stand: Compose-Datei real getestet (siehe `docs/handoff/WP-O2.md`); `swarm/stack.yaml` (Dienst `worker`, `WORKER_REPLICAS`) und die Swarm-Zweige in `setup.sh`/`update.sh` sind **nicht unter Swarm getestet** (nur Syntaxprüfung der Datei).

## Quellen: Mail, Konsumordner, Share-/Scan-API (WP-D4)

Der Worker-Dienst startet `--kinds dms.ocr,dms.verify,dms.export,dms.mail.poll,dms.folder.scan,dms.import.paperless` (Compose real getestet, Swarm nur Syntax). Quellen werden je Mandant über die API angelegt (`/api/v1/tenants/{tenant}/dms/sources`, Recht `dms.source.manage`, Buchhaltung/Owner); jede Quelle ist eine Kette aus Worker-Jobs mit Lease, kein Dauerprozess und kein offener Port.

- **Mail (IMAP, implizites TLS, Port 993).** Das Passwort wird mit AES-256-GCM verschlüsselt in der Datenbank abgelegt; der Schlüssel kommt aus `SECRET_KEY` bzw. dem Secret `lh_secret_key` (Compose/Swarm reichen es an Backend und Worker durch; mindestens 32 Byte: `openssl rand -base64 32`; ein gesetzter, aber kürzerer Schlüssel verhindert den Start mit klarer Meldung; `setup.sh` erzeugt einen passenden). **Geht der Schlüssel verloren oder wechselt er, sind die Passwörter unlesbar** (Quelle meldet `secret_unreadable`) und müssen neu eingetragen werden (`PATCH …/sources/{id}` mit `password`). Backend (Verbindungstest, Anlegen) und Worker brauchen denselben Schlüssel. Ausgehend muss der Worker (und für „Verbindung testen“ das Backend) den IMAP-Host auf Port 993 erreichen; `DMS_MAIL_HOST_ALLOWLIST` (kommagetrennt) beschränkt die erlaubten Hosts (gilt beim Speichern, beim Verbindungstest und bei jedem Abruf im Worker). **WP-H10 Zielschutz:** Als Host sind nur DNS-Namen erlaubt (IP-Adressen werden mit `ip_literal_not_allowed` abgelehnt, weil sonst die Namensprüfung des Zertifikats entfiele); der Name wird vor jedem Verbindungsaufbau aufgelöst, ALLE Adressen werden gegen die Sperrliste geprüft (Loopback, 10/8, 172.16/12, 192.168/16, 169.254/16 inkl. Metadaten, 100.64/10, fc00::/7, fe80::/10, IPv4-in-IPv6) und verbunden wird mit der geprüften IP (Schutz vor DNS-Rebinding), der TLS-Name bleibt der DNS-Name. Verstöße melden einheitlich `target_not_allowed` (kein Port-/Host-Orakel). `DMS_ALLOW_INTERNAL_TARGETS=true` erlaubt interne Ziele ausdrücklich (Mailserver im eigenen Netz, Test/Heim-Setups; gilt auch für den Paperless-Import); der Mail-Port ist standardmäßig nur 993, weitere Ports gibt `DMS_MAIL_PORT_ALLOWLIST` (kommagetrennt, z. B. `143,1993`) frei. Antworten des IMAP-Servers sind je Befehl auf 10 000 Zeilen und 64 MB (mindestens Nachrichtengrenze + 1 MB) begrenzt (`imap_response_too_large`). `DMS_MAIL_CA_PATH` (Pfad einer PEM-Datei im Container, bewusst nicht `…_FILE`: der Entrypoint würde diesen Namen als Secret-Datei lesen) trägt eine eigene CA für interne Server, `DMS_MAIL_TLS_VERIFY=false` schaltet die Zertifikatsprüfung ab (nur Labor; nie je Quelle). Verarbeitet werden **ungelesene** Nachrichten (`UNSEEN`; in einem Mailprogramm gelesene Mails werden nicht aufgenommen). Nach dem Commit werden sie als gelesen markiert und, falls `processed_mailbox` gesetzt ist, verschoben (`UID MOVE`, sonst `UID COPY`); nie gelöscht. Das Zielpostfach muss existieren.
- **Konsumordner.** Ein Volume nur am Worker (`DMS_FOLDER_SOURCE`, Standard benanntes Volume `labhub-consume`, oder ein absoluter Host-Pfad), im Container unter `/mnt/consume`. Der Ordner einer Quelle liegt unter `/mnt/consume/<mandanten-uuid>/<Pfad>` (Kleinbuchstaben-UUID; so erreicht ein Mandant nie den Ordner eines anderen; Symlinks werden nicht verfolgt). Der Nutzer des Workers (UID 10001) braucht Lese-/Schreibrecht, z. B. `install -d -o 10001 -g 10001 /srv/labhub/consume/<mandanten-uuid>/eingang`. Dateien werden erst nach zwei gleichen Messungen (Größe, mtime; plus `stable_seconds`) gelesen und danach nach `processed/` (oder `failed/` bei unbekanntem Typ/zu groß) im selben Ordner verschoben. Im Backend-Container ist der Ordner **nicht** eingebunden (ADR 0003). Swarm: Volume muss auf allen Knoten mit Worker-Replik dasselbe zeigen (NFS) oder die Replik wird an einen Knoten gebunden.
- **Paperless-Import (WP-D6).** Läufe werden über `POST /api/v1/tenants/{tenant}/dms/imports` angelegt (Recht `dms.import.manage`, nur Buchhaltung/Owner; erst `dry_run`, dann `import`; Bericht über `…/imports/{id}/report`). Quelle `export`: Verzeichnis eines `document_exporter`-Exports in einem Volume nur am Worker (`DMS_IMPORT_SOURCE`, Standard benanntes Volume `labhub-import`, im Container **schreibgeschützt** unter `/mnt/import`), Ablage `/mnt/import/<mandanten-uuid>/<Pfad>/manifest.json` (Kleinbuchstaben-UUID; Links werden nicht verfolgt). Quelle `api`: REST-API einer Paperless-ngx-Instanz mit Token (nur Lesen); ausschließlich `https` mit voller Zertifikatsprüfung (TLS ab 1.2), keine Weiterleitungen, Loopback und Link-Local (Metadaten-Adressen) gesperrt; `DMS_IMPORT_HOST_ALLOWLIST` (kommagetrennt, `host` oder `host:port`) beschränkt die erlaubten Hosts und gilt in Backend (beim Anlegen) und Worker. Das Token wird mit `SECRET_KEY` verschlüsselt (wie die Mail-Passwörter, siehe oben). Der Worker braucht dafür ausgehend nur den Paperless-Host. Seit WP-H10 gilt die gemeinsame Zielprüfung (siehe Mail): alle Schreibweisen interner Adressen sind gesperrt, der Host wird vor jedem Lauf aufgelöst und die geprüfte IP für den Connect festgelegt; `DMS_ALLOW_INTERNAL_TARGETS=true` hebt das ausdrücklich auf. `DMS_IMPORT_INSECURE_DEV=true` erlaubt `http` und Loopback und ist nur für Entwicklung und Tests gedacht; nie in Produktion setzen.
- **Share-/Scan-API.** `POST /api/v1/tenants/{tenant}/dms/share` mit `Authorization: Bearer lhp_…` (persönliches Token, Scope `dms.upload`, erzeugt über `POST /api/v1/auth/api-tokens` in einer Sitzung). Kein Idempotency-Key nötig. Minimalstand F-05: nur dieser Scope, Pflichtablauf (Standard 365 Tage), Widerruf sofort. Beispiel: `curl -H "Authorization: Bearer $TOKEN" --data-binary @scan.pdf "https://hub.example.org/api/v1/tenants/$TENANT/dms/share?filename=scan.pdf"`.
- Neue Verarbeitungs-Einstellungen am Worker: `DMS_TENANT_QUOTA_BYTES`, `DMS_DEFAULT_RETENTION_YEARS` (für den Export/Prüf-Job aus D5) und `DMS_MAX_UPLOAD_BYTES` gelten wie am Backend; für Quellen wird die Größe/Quota des Mandanten ebenso durchgesetzt.

## Extraktion und Mail-Vorschau (WP-H10)

Die Dokumenterkennung ist gegen manipulierte Texte (ReDoS) gehärtet: Whitespace-Läufe werden vor der Auswertung auf höchstens 3 Zeichen gekappt, der ausgewertete Text ist auf 50 000 Zeichen begrenzt, und die Extraktion läuft unter einer harten Frist (Standard 5 s, `DMS_EXTRACT_TIMEOUT_MS` 50…30000). Bei Ablauf gilt das Dokument als `other`/unsicher mit Grund `extraction_timeout`; Ingest und Mail-Abruf laufen normal weiter (die Mail wird als verarbeitet markiert, keine Endlosschleife). Das gespeicherte HTML einer Mail wird beim Speichern entschärft (`<meta>`, `<base>`, `<link>` entfernt, `<form>` neutralisiert); die Auslieferung trägt `default-src 'none'; sandbox; frame-src 'none'; base-uri 'none'; form-action 'none'`.

## Härtung (WP-H6)

**Reverse Proxy und Rate-Limit (`TRUSTED_PROXIES`).** Das Rate-Limit der Anmelderouten zählt je Client-Adresse. Standard: keine vertrauten Proxys, dann zählt nur die Adresse der TCP-Verbindung und `X-Forwarded-For` wird ignoriert. Steht das Backend hinter einem Reverse Proxy (Ingress, Traefik, nginx), sehen alle Clients sonst wie der Proxy aus (ein gemeinsamer Zähler). Dann `TRUSTED_PROXIES` auf die Adressen oder Netze der Proxys setzen, kommagetrennt, IPv4/IPv6, optional mit Präfix, z. B. `TRUSTED_PROXIES=10.0.0.0/8,192.0.2.7,fd00::/8` (Beispielwerte). Nur Verbindungen von diesen Adressen werden bei `X-Forwarded-For` von rechts gelesen (der erste nicht vertraute Eintrag ist der Client). Ein ungültiger Eintrag lässt den Start scheitern. Der Proxy muss `X-Forwarded-For` anhängen oder setzen, nie ungeprüft durchreichen; im Swarm ist die Quelladresse hinter dem Ingress-Netz oft die Overlay-Adresse, nicht die des Proxys: Adresse mit einem Test prüfen.

**Speicherquota je Mandant (`DMS_TENANT_QUOTA_BYTES`).** Obergrenze für die Summe aller gespeicherten Dateien eines Mandanten (Originale und abgeleitete Dateien, gleiche Bytes zählen einmal). Standard 1099511627776 (1 TiB). Überschreitung: Upload 413 mit Code `storage_quota_exceeded`. Die Grenze gilt für Uploads; vom OCR-Worker erzeugte Archivdateien zählen mit, werden aber nicht abgelehnt.

**Datenbankrollen und Audit-Log.** Die Migration `018_audit_hardening` entzieht dem Anwendungsbenutzer und PUBLIC auf `audit_log` UPDATE, DELETE, TRUNCATE und TRIGGER (übrig: INSERT, SELECT); die Trigger aus `011_audit_log` bleiben als zweite Schicht. Seit WP-H8 gibt `019_audit_trigger_privilege` dem Eigentümer TRIGGER zurück (UPDATE, DELETE und TRUNCATE bleiben entzogen): Ohne dieses Recht scheiterte `dms_021_revision` (Trigger auf `audit_log`) mit `permission denied for table audit_log`, sobald die Datenbankrolle eine normale Einzelrolle war (`CREATE ROLE … LOGIN`, wie `setup.sh` sie anlegt; Compose-Dev und Tests laufen als Superuser und zeigten es nicht). Die Migrationen laufen damit vollständig mit einer nicht-privilegierten Eigentümerrolle (kein SUPERUSER, CREATEDB oder CREATEROLE nötig); abgesichert durch `MigrationRoleTests`. Bestehende Installationen, die 018 schon angewandt haben, migrieren beim nächsten `migrate` weiter. Eine Installation, bei der `dms_021_revision` bereits mit diesem Fehler abgebrochen ist, kann einen halb angewandten Schritt hinterlassen haben (DDL ohne Transaktion, Fehler `column … already exists` beim Wiederholen): dann die Datenbank aus der Sicherung wiederherstellen oder die in `dms_021_revision` angelegten Objekte von Hand entfernen. Mit **einer** Rolle, die zugleich Eigentümerin der Tabellen ist, ist das nur eine Hürde, kein Schutz: Eigentümer können per `GRANT` oder `ALTER TABLE audit_log DISABLE TRIGGER …` alles zurückholen. Empfehlung für den Betrieb (noch nicht von `setup.sh` umgesetzt): zwei Rollen. `labhub_owner` (Eigentümerin, nur für den Migrationsjob, `DB_USER` des Dienstes `migrate`) und `labhub_app` (Laufzeit von Backend und Worker, Mitglied von nichts, ohne Eigentum). Nach jeder Migration:

```
GRANT USAGE ON SCHEMA public TO labhub_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO labhub_app;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO labhub_app;
REVOKE UPDATE, DELETE, TRUNCATE ON audit_log FROM labhub_app;
```

Die Laufzeitrolle darf keine DDL-Rechte haben (`CREATE` im Schema entziehen) und kein Superuser sein. Offen bleibt, dass Tabellen ohne eigene Trigger (z. B. `dms_*`) für die Laufzeitrolle voll schreibbar sind; das ist gewollt. Superuser und Eigentümer umgehen jede dieser Maßnahmen.

## PWA-Auslieferung und Gesamtlauf (WP-H9)

**PWA.** Das Backend-Image enthält die gebaute PWA (Dockerfile-Stufe `pwa`: `npm ci`, `npm run build`) fest unter `/usr/share/lab-hub/pwa`; zur Laufzeit wird nichts geschrieben (read-only Root bleibt). Das Backend liefert sie für `GET`/`HEAD` auf Pfade ohne Backend-Route aus; `/api/*`, `/health`, `/ready` bleiben unberührt (unbekannte `/api`-Pfade: 404 `application/problem+json`, nie `index.html`). Pfade ohne Dateiendung liefern `index.html` (Deep-Links wie `/dms/inbox`), fehlende Dateien mit Endung 404. Pfad-Traversal (`..`, `%2e%2e`, `\`, Symlinks aus dem Verzeichnis heraus, versteckte Dateien) ist abgewiesen.

| Variable | Bedeutung |
| --- | --- |
| `PWA_DIR` | Verzeichnis mit `index.html`; im Image gesetzt. Ausdrücklich gesetzt und ohne `index.html`: Startfehler. Ohne Angabe und ohne Standardverzeichnis (`swift run`): keine Auslieferung. |
| `PWA_ENABLED` | `false` schaltet die Auslieferung ab (reines API-Backend, z. B. wenn ein Proxy die PWA ausliefert). |
| `PWA_HSTS_MAX_AGE` | Sekunden; sendet `Strict-Transport-Security` an PWA-Antworten. Nur hinter einem TLS-Proxy setzen (Standard aus). |

Cache: `_app/immutable/*` mit `public, max-age=31536000, immutable`; `index.html`, `version.json` und alle übrigen Dateien mit `no-cache` (ETag für `index.html`). Header an PWA-Antworten: `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, `Permissions-Policy` (Kamera, Mikrofon, Standort aus), optional HSTS.

CSP: `default-src 'self'; script-src 'self' 'sha256-<Hash des Start-Inline-Skripts>'; style-src 'self' 'unsafe-inline'; img-src 'self' blob: data:; font-src 'self'; connect-src 'self'; frame-src 'self' blob:; worker-src 'self'; manifest-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'`. Strategie: SvelteKit schreibt genau ein Inline-Skript in `index.html`; das Backend berechnet beim Start dessen SHA-256 aus der ausgelieferten Datei und trägt es ein (kein Nonce, weil die Datei statisch ist; kein `unsafe-inline`/`unsafe-eval` für Skripte). `style-src 'unsafe-inline'` ist wegen `style`-Attributen von SvelteKit/Tailwind nötig. `blob:` für Bild- und PDF-/Mail-Vorschau, `frame-src 'self'` für die Datei-Routen. Die Datei-Routen der API senden weiterhin ihre eigene, strengere CSP. Ein vorgeschalteter Proxy darf diese Header nicht überschreiben.

**Alle Umgebungsvariablen** stehen mit Erklärung in `.env.example` oder in den Abschnitten oben; `scripts/check-env-docs.sh` (Teil von `scripts/ci.sh`) schlägt fehl, wenn eine im Backend gelesene Variable in keiner der beiden Stellen vorkommt. Zusätzlich: `SETUP_TOKEN` (nur Bootstrap, danach entfernen), `OBJECT_STORE` (`db` Standard, `fs` mit `OBJECT_STORE_FS_PATH`, nur ein Host; `s3` noch nicht implementiert), `HUB_REPLICAS` (nur Warnung bei `fs` mit mehr als einer Replik; die Konfiguration wird beim Start geprüft, Fehler brechen den Start ab), `DMS_DEFAULT_RETENTION_YEARS`, `DMS_MAX_UPLOAD_BYTES`, `DMS_FOLDER_ROOT`/`DMS_IMPORT_ROOT` (im Worker-Container fest `/mnt/consume` bzw. `/mnt/import`; nicht ändern), `DMS_MAIL_SESSION_TIMEOUT_SECONDS` (10 bis 3600), `DMS_REGEX_TIMEOUT_MS` (10 bis 5000, Zeitlimit je Regel-Regex), `OCR_TMPDIR` (Worker: `/tmp`), `WORKER_ENABLE_SELFTEST` (nur Tests, nie in Produktion).

**Getrennte Migrationsrolle.** `setup.sh` legt eine einzige Datenbankrolle an. Für Produktion empfohlen: der Dienst `migrate` läuft mit `DB_USER`/`DB_PASSWORD(_FILE)` der Eigentümerrolle, Backend und Worker mit einer Laufzeitrolle ohne Eigentum und ohne DDL-Recht (Befehle im Abschnitt Härtung). Dafür dem Dienst `migrate` eigene `DB_USER`/Secret-Werte geben; Compose-Datei und `setup.sh` setzen das noch nicht um (offen).

**Gesamtlauf (real getestet, siehe `docs/handoff/WP-H9.md`).** Image `docker build -t lab-hub:h9 .`, Worker `docker build -f Dockerfile.worker -t lab-hub:h9-worker .`; Compose-Stack mit eigenem Projektnamen, Port und `setup.sh --non-interactive` (Variablen `LH_*`). Stack-E2E: `cd pwa && E2E_PORT=<port> E2E_SETUP_TOKEN=<token> npm run test:e2e:stack`. Der Stack muss mit `SETUP_TOKEN` gestartet werden (Datei `deploy/.env`, danach entfernen). Swarm bleibt ungetestet (nur Syntaxprüfung).
